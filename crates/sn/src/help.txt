## auth
Start here: `auth login` connects an instance and saves it as a profile. A profile keeps the address and the sign-in, so later commands need no flags. `auth status` says whether it still works.
$ sn auth login --instance acme
$ sn auth status

## auth login
effect: local
Opens your default browser (never a private or controlled window), so company SSO, device sign-in and browser extensions work. The link is always printed too: open it anywhere, then paste the code or the address of the last page. Other methods: basic, session (MFA), password, client-credentials, jwt, api-key, token, cookie, certificate.
Agents: the first call returns `data.url` for the person to open. Finish with `--code`, or add `--wait` (with a client id) to wait for the browser.
> Sign in through the browser and save the profile `prod`
$ sn auth login --instance acme --profile prod
> User name and password, read from stdin
$ sn auth login -i acme --method basic --username ada --secret-stdin
> Start as an agent, then finish with the code that the person gives
$ sn auth login -i acme --agent
$ sn auth login --code CODE --agent

## auth logout
effect: local
Revokes the OAuth token on the instance, then removes the credential from this computer. The profile itself stays, so `auth login` signs in again without more settings.
$ sn auth logout --profile prod
> Remove it here and leave the token valid
$ sn auth logout --local

## auth status
effect: read
Shows the instance, the method, the user and the expiry of the token, and asks the instance whether the sign-in works. Exit code 2 means that you must sign in again.
$ sn auth status
> Look at the saved settings only
$ sn auth status --offline --agent

## auth refresh
effect: local
Exchanges the refresh token for a new access token. Commands do this by themselves; use it before a long job, or to test the refresh token.
$ sn auth refresh --profile prod

## auth token
effect: local
Prints the live credential so that curl or another tool can use the same sign-in. The output is a secret: do not log it or paste it into a chat.
> A header line for curl
$ sn auth token --as headers
> Only the bearer token
$ sn auth token --as bearer

## auth switch
effect: local
Every command without `--profile` then uses this profile.
$ sn auth switch prod

## auth register
effect: confirm
For administrators, once per instance: creates the OAuth client (Application Registry, authorization code with PKCE) that lets the browser return to this computer by itself. Users then sign in with `--client-id` and paste nothing. `--print` shows the settings so that you can enter them by hand.
$ sn auth register --print
$ sn auth register --name "sn CLI" --yes

## init
effect: local
Asks for the instance and how you sign in, signs in, and saves the profile. It takes the same flags as `auth login`.
$ sn init
$ sn init --instance acme

## profile
Each profile is one instance and one sign-in. Choose one with `--profile NAME`, `SN_PROFILE`, or `profile use`.
$ sn profile list
$ sn profile use prod

## profile list
effect: local
Lists the saved profiles, their instances and methods, and which one is the default. Nothing is sent to an instance.
$ sn profile list
$ sn profile list --agent

## profile show
effect: local
Prints the settings of a profile: address, method, proxy, certificates, read-only. Secrets are never printed.
$ sn profile show prod

## profile use
effect: local
Makes the profile the default, as `auth switch` does.
$ sn profile use dev

## profile add
effect: local
Signs in and saves the result under a name. It takes the flags of `auth login`.
$ sn profile add dev --instance acmedev
$ sn profile add ci -i acme --method api-key --secret-stdin

## profile set
effect: local
Changes settings of a saved profile without signing in again. A read-only profile refuses every write, whatever the command or its flags say: use one for agents that must only look.
$ sn profile set prod --profile-read-only true
$ sn profile set prod --bypass-proxy localhost,.corp.example

## profile remove
effect: confirm-local
Deletes the profile and its credential from this computer. The instance does not change.
$ sn profile remove old --yes

## profile login
effect: local
Signs in again with the settings of the selected profile. The same as `auth login`.
$ sn profile login --profile prod

## profile logout
effect: local
Removes the credential and keeps the profile. The same as `auth logout`.
$ sn profile logout --profile prod

## profile status
effect: read
Says whether the sign-in of the profile works. The same as `auth status`.
$ sn profile status --profile prod

## profile refresh
effect: local
Gets a new access token. The same as `auth refresh`.
$ sn profile refresh --profile prod

## tui
effect: depends
Opens a full-screen workspace: queues on the left, records in the middle, and the record with its conversation, related records, files and SLAs. Each change is shown before it is sent. Press `?` for the keys. It needs a terminal, so agents use the other commands.
$ sn tui
> Start with one table and a filter
$ sn tui incident --query 'active=true^priority=1'

## get
effect: read
With a record: prints its fields, catalog variables, comments and work notes together. With one of the commands below: one piece of your context, such as your open work or the current update set.
Returns one object for a record.
> A record by number, link, or table and sys_id
$ sn get INC0010001
$ sn get incident:SYS_ID --agent
> Your open work
$ sn get mine

## get script
effect: read
Finds a script by name in script includes, business rules, client scripts, UI actions, UI scripts, scheduled jobs and fix scripts. Several matches are listed, so that you can choose one with `--type` or `--scope`.
$ sn get script JSUtil

$ sn get script MyUtil --type include --source > MyUtil.js

## get instance

Shows the release, the patch and the node that answered.

## get mine
effect: read
Lists open tasks assigned to you, then unassigned tasks of your groups, newest first.
$ sn get mine

## get last
effect: read
Shows the task that you updated last. With `--table` it looks in another table, for example your last script.

Reads the system log (syslog), newest first. Most instances allow it to administrators only.

## table
Works on every table that you can read. Find names with `schema tables`, columns with `schema columns TABLE`, and values with `choices TABLE FIELD`. The short form `sn table incident` lists, and `sn table incident:INC0010001` reads one record; writes are never implied.
$ sn table list incident -q 'active=true^priority=1' -f number,short_description
$ sn table get incident:INC0010001

## table list
effect: read
Reads records that match an encoded query. Values are labels; `--display-value false` gives the raw values that queries and writes need. `meta.total` has the number of matches, and `meta.next` tells how to get the next page. The instance ignores a query term with a wrong field name, so check names first.
Returns a list of records.
$ sn table list incident -q 'priority=1^ORDERBYDESCsys_created_on' -f number,short_description -n 20
> Fields of a referenced record
$ sn table list incident -f number,caller_id.email --agent
> Every match, one JSON record per line
$ sn table list cmdb_ci_server --all -f name,ip_address > servers.jsonl

## table get
effect: read
Reads one record. Name it by number, `table:number`, `table:sys_id`, a link from the browser, or a table and a sys_id.
Returns one record.
$ sn table get INC0010001
$ sn table get incident SYS_ID -f number,state --display-value all --agent

## table create
effect: write
Creates a record and returns it. `--field` sends raw values; add `--input-display-value` to send labels.
$ sn table create incident -F short_description="VPN down" -F urgency=2
> The whole record as JSON, and only look at the request
$ sn table create u_asset -D @asset.json --dry-run --agent

## table update
effect: write
Changes the fields that you name and leaves the others (PATCH). `name=` empties a field, and `name=@file` reads the value from a file.
$ sn table update incident:INC0010001 -F state=2 -F work_notes="Checked the gateway"
$ sn table update sys_script_include SYS_ID -F script=@MyUtil.js --agent

## table replace
effect: write
Sends the record with PUT. On most tables the instance treats it as `update`; use `update` unless an integration needs PUT.
$ sn table replace incident SYS_ID -D @incident.json

## table delete
effect: confirm
Deletes one record for ever. It reads the record first and shows what it is.
$ sn table delete u_asset SYS_ID
$ sn table delete u_asset SYS_ID --yes --agent

## table count
effect: read
Counts the matches on the server and reads no records. Use `aggregate` to group.
$ sn table count incident -q active=true

## gr
effect: read
Reads records and fields of their references in one GraphQL request, where the Table API needs several. Use it for deep dot-walks and when you want values and labels together.
$ sn gr incident -f number,caller_id.manager.email -q active=true -n 20
$ sn gr incident -q active=true --count --agent

## aggregate
effect: read
Counts, sums and averages on the server, with groups. It is much faster than reading the records.
> How many active incidents has each group, by priority
$ sn aggregate incident -q active=true --group-by assignment_group,priority
> Average and largest reassignment count
$ sn aggregate incident --avg-fields reassignment_count --max-fields reassignment_count --agent
> Only groups with more than three
$ sn aggregate incident --group-by category --count --having 'count^category^>^3'

## graphql
effect: depends
Sends a GraphQL document to the instance. A document with a mutation is a write: `--read-only` refuses it and `--dry-run` shows it. Errors in the answer are command errors.
$ sn graphql '{ GlideRecord_Query { incident { _results { number { value } } } } }'
$ sn graphql @query.graphql --var id=INC0010001 --agent

## journal
effect: read
Prints the comments and work notes of a record, newest first, with the time and the author. Add one with `incident note`, or with `table update -F work_notes=...` on other tables.
$ sn journal INC0010001
$ sn journal change_request:CHG0030001 --work-notes --limit 5 --agent

$ sn variables get RITM0010001

## variables get
effect: read
Reads the variables of a requested item or a record producer's record. A catalog task shows those of its request item.
$ sn variables get RITM0010001

## variables set
effect: write
Writes variables, reads them back, and fails when the instance did not store one. Values are raw: a sys_id for a reference, `true` or `false` for a checkbox.
$ sn variables set RITM0010001 -F color=black -F needs_dock=true

## watch
effect: read
Prints inserts, updates and deletes as they happen, through the instance's message bus. It runs until you stop it, so agents and scripts set a limit. With `--agent` each event is one JSON line.
> Every change to critical incidents
$ sn watch incident -q priority=1
> One record, until its state changes once
$ sn watch INC0010001 --on-change state --max-events 1
> At most one minute, one JSON line for each event
$ sn watch incident -q active=true --duration 60 --agent

## catalog order
effect: confirm
The instance accepts wrong choices, references to the wrong table and unknown names without a word, so every value is checked first. Then it shows the order and asks. Pass values with `--var`, and secrets with `--vars-file`. With `--data` or `--field` the body is sent as it is, without checks. `--dry-run` does everything except the order. Returns the request number.

$ sn catalog order "Standard Laptop" --vars-file laptop.yaml --requested-for ada --yes --agent
